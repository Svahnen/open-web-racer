# Architecture

Open Web Racer is a browser-first, self-hosted multiplayer racing game. A Rust server owns the race; a Rust/WebAssembly client renders it. All shipped cars and tracks are generated by the project and need no external data.

## Components

| Component | Crate or path | Role |
| --- | --- | --- |
| Simulation | `crates/sim` | Fixed-step, deterministic vehicle and race simulation (60 Hz). Independent of render frame rate; shared by server and client. |
| Protocol | `crates/protocol` | Versioned binary (postcard) messages carried over WebSocket. See [NETWORK_PROTOCOL.md](NETWORK_PROTOCOL.md). |
| Server | `crates/server` | Axum process: serves the web app, `/healthz` and `/ws`; hosts rooms, countdowns, laps, finish order and computer opponents. |
| Client | `crates/client`, `crates/render`, `web/` | WASM client, `wgpu` renderer (WebGPU or WebGL2, Canvas 2D fallback), input, prediction and remote interpolation, HUD and audio. |
| AI drivers | `crates/ai` | Game-neutral computer drivers (lane choice, target speed, steering, recovery, catch-up). See [AI_DRIVERS.md](AI_DRIVERS.md). |
| Content | `crates/pack-schema`, `crates/content` | Content pack format (RCP v1), validation and loaders. See [CONTENT_PACK.md](CONTENT_PACK.md). |
| Generators | `crates/trackgen`, `crates/cargen` | Deterministic procedural tracks and cars. See [TRACKGEN.md](TRACKGEN.md). |
| Example model | `crates/example-model` | A tiny vehicle model provider showing how a separate crate plugs into the engine. |
| Tooling | `crates/test-client`, `crates/trace-compare`, `crates/xtask` | Headless test client, trace comparison and build helpers. |

## Authority and timing

The server is authoritative. Clients submit driver intent (throttle, brake, steering, gear requests, reset), never positions. The server simulates canonical state and sends snapshots; clients predict locally for responsiveness and reconcile to the snapshots. Rendering frequency never advances simulation time. Cross-platform bit-identical floating point is not a requirement; tests use documented tolerances.

## Deployment shape

One process serves the browser application and the WebSocket on the same origin. Each instance is its own lobby universe, with no central account, matchmaking or master-server dependency. See [DEPLOYMENT.md](DEPLOYMENT.md).

## Extension points

- **Vehicle models**: the simulation consults a vehicle model registry; a crate can register a model and receive its parameters through `SetCarModel`.
- **Content providers**: the server accepts registered content providers beside the built-in generated content.
- **Web plugins**: `window.RacerPlugins` hooks (HUD, audio, scene source, paint, car-model changes) let a separate package extend the page. See [PLUGINS.md](PLUGINS.md).

## Security invariants

Bound and validate all network and content input. Never trust client-provided race outcomes. Do not expose filesystem paths or tooling through the server. Do not commit executables or third-party assets.
